# План добавления SDXL в локальный стек

Дата: 21 сентября 2026. Статус: предложение для обсуждения, реализация не начата.
Запрошены HTTP API и веб-интерфейс. Этот документ не разрешает установку новых
пакетов: список зависимостей необходимо согласовать перед реализацией.

## 1. Что есть в проекте

- `compose.yaml`: отдельные профили `qwen` и `gemma`, оба используют CUDA-образ
  llama.cpp и обе GPU; порты хоста 8080 и 8081. Веса GGUF подключаются из `models`.
- `Makefile`: команды переключают Qwen/Gemma, останавливая предыдущую модель;
  инфраструктура запускается независимо. Это подходящий образец для SDXL.
- `dsh/Dockerfile`: образ интерфейса агента, а не универсальный сервер моделей.
  SDXL следует разместить в отдельном образе и сервисе.
- Prometheus, Grafana, GPU exporter, Loki и Alloy уже настроены.
  `config.alloy` пропускает только `qwen|gemma`; список моделей в dashboard логов
  тоже фиксированный. Метрики существующего inference dashboard относятся к LLM.
- `prepare.sh` создает `.env` только с нуля и отказывается работать при его наличии.
  Повторный запуск не подходит для добавления SDXL в существующую установку.
- `download-model.sh` рассчитан на один GGUF Qwen; SDXL требует отдельной загрузки.
- `smoke-test.py` проверяет chat, streaming и tools; для изображений нужен свой тест.
- README частично отстает от Compose: встречаются сервис `llama`, старые параметры
  и порт Grafana 3000, тогда как текущий порт хоста 3055. Новые инструкции должны
  опираться на реальные сервисы `qwen`/`gemma` и текущий Makefile.
- `docker-wsl.sh` обеспечивает работу с публичными registry без Windows credential
  helper; Makefile допускает переопределение `COMPOSE`, это следует сохранить.

Изучены конфигурация, скрипты запуска/загрузки/тестов и настройки мониторинга.
GPU и контейнеры не запускались. В доступной директории `git status` сообщает,
что это не Git-репозиторий; проверка изменений через Git здесь недоступна.

## 2. Предлагаемое решение

Создать образ `local/ml-sdxl` с PyTorch CUDA, Hugging Face Diffusers и небольшим
HTTP-приложением. Выбор собственного тонкого сервиса позволяет явно контролировать
размещение модели, очередь и контракт API, используя готовый движок Diffusers.
Внутри одного процесса: одна модель, один исполнитель генерации, ограниченная
очередь, API и статический веб-интерфейс. Несколько серверных workers запрещены,
поскольку каждый загрузит дополнительную копию весов.

Модель: `stabilityai/stable-diffusion-xl-base-1.0`, Diffusers layout, safetensors,
FP16-веса. Base работает самостоятельно; refiner для первого этапа не нужен.
Основание: [карточка SDXL Base](https://huggingface.co/stabilityai/stable-diffusion-xl-base-1.0).

Первая версия: text-to-image, prompt, negative prompt, seed, число шагов,
guidance scale и несколько проверенных размеров. Refiner, LoRA, ControlNet,
img2img, обучение и интеграция в DSH вынесены за рамки первого этапа.
SDXL не следует регистрировать в DSH как chat-completions provider.

## 3. GPU и память

| Режим | Размещение | Назначение |
|---|---|---|
| Основной: 4070 Ti Super 16 GiB | Весь pipeline на одной GPU | Первый обязательный режим приемки |
| Дополнительный: 4070 Ti Super + 3080 Ti 12 GiB | Компоненты одного pipeline распределены между GPU | Проверяемая опция при необходимости освободить VRAM |

Предлагаемый старт: 1024x1024, одно изображение, один активный запрос,
30 шагов, guidance scale 5, FP16 для UNet и текстовых энкодеров.
Предполагается, что базовая модель при таком режиме поместится в 16 GiB;
это инженерная гипотеза до замеров на целевой машине, а не гарантия.
Размер checkpoint не равен пику VRAM: нужны также активации, VAE decode,
CUDA context и резерв аллокатора. Цель приемки: минимум 1 GiB свободной VRAM
на каждой задействованной карте под нагрузкой, желательно больше на карте дисплея.

Для одной карты использовать штатное размещение pipeline на CUDA. Не включать
CPU/sequential/group offload и перенос весов на диск. Сохранить предусмотренное
моделью повышение точности VAE на GPU, если оно нужно для стабильного decode;
не принуждать весь VAE к FP16 ценой черных изображений или NaN.
Начать со штатного PyTorch attention backend; compile и дополнительные attention
библиотеки оценивать только после базовой приемки.

Две GPU не образуют общий непрерывный пул 28 GiB. Для дополнительного режима
сначала проверить `device_map="balanced"`, GPU-бюджеты `max_memory` и фактический
`hf_device_map` на закрепленной версии Diffusers. Желаемое размещение:
UNet на 4070 Ti Super, текстовые энкодеры и при необходимости VAE на 3080 Ti.
Автоматическая стратегия не гарантирует именно такую карту. Если она непригодна,
отдельно проверить поддерживаемое размещение компонентов и передачу тензоров;
не обещать работоспособность произвольного словаря pipeline device_map.
При CPU/disk-размещении обязательных нейросетевых компонентов запуск отклонять.

Не дробить UNet между картами в первой версии: повторяющийся обмен на каждом
шаге может увеличить задержку. Сравнить время одного изображения с одной GPU;
вторая карта нужна прежде всего для памяти, ускорение не гарантируется.
`max_memory` ограничивает размещение весов, но не весь пик исполнения.
VAE tiling рассмотреть при пике decode; VAE slicing в первую очередь полезен
для нескольких изображений, поэтому не считать его решением для batch=1.
Основание: [управление памятью Diffusers](https://huggingface.co/docs/diffusers/optimization/memory).

Полностью исключить CPU/RAM нельзя: загрузка checkpoint, токенизация, HTTP,
очередь, PNG-кодирование и системные службы используют память хоста.
Цель: вычисления нейросети и ее рабочие веса на GPU без постоянного CPU-offload.
Пиковую RAM при загрузке измерять отдельно от рабочего режима. В WSL/Windows
контролировать Shared GPU memory: размещение тензоров на CUDA само по себе
не исключает вытеснение драйвером. Ограничения платформы описаны в
[NVIDIA CUDA on WSL](https://docs.nvidia.com/cuda/wsl-user-guide/index.html).

Qwen и Gemma перед запуском SDXL останавливаются: текущие конфигурации LLM
используют обе карты. Их одновременная работа с SDXL не входит в базовый режим.

## 4. Пошаговая реализация

### Шаг 1. Зафиксировать зависимости и окружение

До установки согласовать список: PyTorch с CUDA, Diffusers, Transformers,
Accelerate, safetensors, huggingface_hub, Pillow, FastAPI, Uvicorn,
prometheus-client и необходимые транзитивные зависимости.
Отдельно зафиксировать решение о штатном watermark и его зависимости.
Для UI предложен обычный HTML/CSS/JS без Node-сборки и новых frontend-пакетов.

Подобрать совместимые закрепленные версии Python/PyTorch/CUDA/Diffusers,
проверить поддержку Ampere и Ada, зафиксировать digest базового образа и
воспроизводимый список зависимостей. Сверить драйвер, UUID GPU, свободную VRAM,
RAM, диск и фактическую платформу Linux либо WSL2. Ничего не обновлять автоматически.

Результат: согласованный стек и конкретные версии для сборки.

### Шаг 2. Подготовить отдельное хранилище модели

Добавить `download-sdxl-model.sh` и служебный downloader внутри нового образа.
Скачивать только нужный Diffusers snapshot: конфиги, tokenizer/tokenizer_2,
text_encoder/text_encoder_2, UNet, VAE и scheduler с выбранными FP16-файлами.
Не скачивать все альтернативные форматы и FP32-копии репозитория.

Использовать закрепленный commit revision, каталог `models/sdxl-base-1.0`,
отдельные manifest/revision/checksums; не перезаписывать данные Qwen.
Загрузка должна быть возобновляемой и завершаться проверкой полноты snapshot.
Локальные SHA256 фиксируют целостность повторного чтения, а не удостоверяют автора.
Сверить набор файлов с загрузчиком до объявления модели готовой.

Веса не включать в Docker image. На runtime монтировать их read-only и загружать
локально с запретом сетевой дозагрузки. Сборка образа не должна запускать скачивание
многогигабайтной модели. Подход основан на
[документации загрузки Diffusers](https://huggingface.co/docs/diffusers/using-diffusers/loading).

Результат: воспроизводимая загрузка и старт из локального snapshot без интернета.

### Шаг 3. Собрать образ и загрузчик pipeline

Добавить `sdxl/Dockerfile`, `sdxl/.dockerignore`, файлы зависимостей и приложение.
Контекст сборки ограничить `sdxl`, исключив существующие GGUF и результаты.
Запускать от непривилегированного пользователя; отдельно обеспечить права
на каталог результатов. Загружать модель один раз при старте.

Поддержать режимы `single` и `dual` с отдельными SDXL-переменными окружения.
Идентифицировать карты по UUID, логировать соответствие UUID и логических CUDA
индексов. Учитывать перенумерацию после ограничения видимых GPU контейнера.
Проверять устройства параметров модели и сообщать понятную ошибку при отсутствии
CUDA, неполном snapshot или недопустимом размещении.

Разделить liveness и readiness. Readiness успешна после загрузки и небольшого
прогрева; размер healthcheck start period подобрать по реальному холодному старту.
Обработать OOM без автоматического CPU fallback; при невозможности восстановить
рабочий pipeline перевести readiness в ошибку и корректно завершить процесс.

Результат: один процесс с одной моделью и диагностируемым состоянием.

### Шаг 4. Реализовать HTTP API и очередь

Предлагаемый контракт:

| Метод и путь | Назначение |
|---|---|
| `GET /health/live` | Процесс отвечает |
| `GET /health/ready` | Модель готова к генерации |
| `POST /api/generations` | Создать задание, вернуть 202 и ID |
| `GET /api/generations/{id}` | Статус, прогресс, параметры и ошибка |
| `GET /api/generations/{id}/image` | Скачать готовый PNG |
| `DELETE /api/generations/{id}` | Отменить ожидающее или активное задание |
| `GET /metrics` | Метрики Prometheus |

Валидировать prompt, negative prompt, seed, шаги, guidance и разрешение.
Для первой версии разрешить batch=1 и небольшой список размеров, начиная с
1024x1024; остальные размеры включать только после замеров.
Согласовать верхнюю границу длины prompt с токенизаторами и явно сообщать об
усечении. API не обещает полную совместимость с OpenAI Images.

Ограничить очередь, например четырьмя ожидающими заданиями; избыток отклонять
с 429. Генерация не блокирует HTTP event loop. Отмена активного задания
проверяется между шагами pipeline, а слот освобождается после завершения GPU-работы.
При рестарте незавершенные задания отмечаются прерванными; не обещать их продолжение.
PNG и JSON-метаданные сохранять атомарно в `outputs/sdxl` с ID сервера, без путей
от клиента; определить срок хранения или квоту и очистку результатов.

Метаданные: revision, версии runtime, seed, параметры, scheduler, время и GPU-режим.
Повторяемость проверять внутри закрепленного окружения; побитовое совпадение
между разными GPU и версиями библиотек не гарантировать.

Результат: документированный API с ограниченной нагрузкой и обработкой ошибок.

### Шаг 5. Добавить веб-интерфейс

Раздавать UI из того же сервиса и использовать тот же API и очередь.
Форма: prompt, negative prompt, размер, шаги, guidance, seed, запуск и отмена.
Показывать ожидание/генерацию/ошибку, изображение, фактический seed, параметры
и скачивание PNG. Состояние задания восстанавливать по ID после обновления страницы.
Историю ограничить политикой хранения сервера.

Проверить desktop/mobile, длинные промпты, загрузку изображения, повторный запрос,
переполненную очередь и недоступный backend. Не загружать отдельную модель для UI.

Результат: доступный локально интерфейс генерации без отдельного frontend-сервера.

### Шаг 6. Встроить в Compose и Makefile

Добавить профиль и сервис `sdxl`, образ `local/ml-sdxl`, общий logging/restart,
healthcheck, volume модели read-only и volume результатов read-write.
Предлагаемый адрес API/UI: `127.0.0.1:8082`; свободность порта проверить перед запуском.
Контейнер слушает `0.0.0.0`, публикация хоста ограничена loopback.
Режим single получает только 4070 Ti Super; dual получает обе выбранные GPU.

Добавить SDXL-переменные и отдельную процедуру подготовки существующей `.env`,
сохраняющую пароли и текущие image digests. Не запускать `prepare.sh` заново
ради обновления существующего окружения.

Добавить цели `sdxl`, `logs-sdxl`, сборку/загрузку модели; дополнить `models-stop`,
`status`, `stop`, `down`. Перед SDXL останавливать Qwen/Gemma, а перед любой LLM
останавливать SDXL. При ошибке остановки не запускать следующую модель.
Сохранить `.NOTPARALLEL`; отдельно указать, что она не блокирует два независимых
процесса make, а ручной `compose up` обходит переключение.

Сохранить поддержку `COMPOSE="bash ./docker-wsl.sh compose"`.
Проверять фактическое освобождение VRAM, не только статус контейнера.
Остановка и переключение не удаляют веса, результаты или named volumes.

Результат: третий тип модели управляется существующим способом.

### Шаг 7. Подключить наблюдаемость

Добавить scrape target `sdxl`, счетчики запросов/изображений/ошибок/OOM,
histogram времени генерации, глубину очереди и готовность модели.
Не включать prompt, ID заданий и seed в labels метрик.
Добавить отдельный SDXL dashboard: секунды на изображение, очередь, ошибки,
память и загрузка GPU. LLM token metrics к SDXL не применять.

Добавить SDXL в Alloy-фильтр и dashboard логов. Сверить `LOG_PROJECT` с реальным
Compose project: сейчас fallback Alloy `qwen-local`, а `name` Compose `ml-local`.
Сохранить совместимость существующего label `job="llm-logs"` либо обновить все
зависимые запросы согласованно. Не писать промпты и изображения в логи по умолчанию.
Учесть отключенный профиль в alerts, чтобы остановленный SDXL не создавал
постоянный ScrapeTargetDown; различать отсутствие scrape и неготовность модели.

Результат: изображения и LLM наблюдаются в общей инфраструктуре.

### Шаг 8. Проверить функциональность и ресурсы

Без GPU: тесты валидации API, переполнения очереди, отмены, восстановления статусов
после рестарта и отказа при CPU-размещении; pipeline подменять тестовым объектом.
Проверить Compose для single/dual и сценарии Makefile в dry-run.

На GPU: `smoke-test-sdxl.py` должен дождаться readiness, создать задание,
дождаться результата, декодировать PNG и проверить размер и непустое содержимое.
Визуально проверить несколько разных промптов; непустые пиксели не доказывают
корректное качество. Проверить negative prompt, seed, отмену и ошибки.

Провести одинаковый benchmark на одной и двух GPU: холодный запуск, прогрев,
не менее 10 последовательных генераций 1024x1024 и 30 минут типичной работы.
Измерять wall time, peak allocated/reserved отдельно на каждой CUDA GPU,
свободную VRAM драйвера, RSS/RAM контейнера и WSL Shared GPU memory при наличии.
Пик VAE decode измерять вместе с denoising, а не только загрузку весов.

При нехватке памяти: освободить GPU от других моделей, проверить attention backend,
испытать VAE tiling, затем dual-размещение. Уменьшенный размер предлагать явно;
не менять незаметно параметры запроса и не включать CPU-offload.

Результат: таблица фактических измерений и подтвержденные ограничения API.

### Шаг 9. Документация и приемка

Обновить README разделом SDXL: подготовка, запуск single/dual, API-пример,
адрес UI, выбор GPU, замеры памяти, диагностика OOM и переключение обратно на LLM.
Задокументировать версии, revision, хранение результатов и лицензию модели.
Для отката достаточно остановить SDXL и вернуть нужный профиль LLM;
удаление volumes и результатов не требуется.

Критерии завершения:

- SDXL генерирует 1024x1024 на 4070 Ti Super без CPU-offload и OOM в серии запросов.
- Дополнительный dual-режим проверен отдельно; польза и ограничения измерены.
- API и UI используют один экземпляр pipeline и соблюдают ограничение очереди.
- Перезапуск сохраняет готовые результаты; отмена и ошибки не оставляют слот занятым.
- Запуск с локальными весами работает без доступа к Hugging Face.
- Переключение Qwen/Gemma/SDXL освобождает VRAM и сохраняет рабочие данные.
- Метрики, логи и UI проверены; существующие LLM проходят свои smoke-проверки.

## 5. Порядок выполнения после согласования

Сначала зависимости и snapshot, затем single-GPU pipeline, API и UI,
интеграция Compose/Makefile и мониторинг. После приемки одной карты проверить
dual-режим тем же набором запросов. Финальный выбор режима делать по измерениям.

Документ описывает будущие изменения. Пакеты и модели не устанавливались,
образы не собирались, текущие сервисы и конфигурация не изменялись.
