# SDXL Base 1.0

Локальный text-to-image сервис: API и веб-интерфейс используют один pipeline
и одну очередь. Основной режим: RTX 4070 Ti Super, FP16, 1024x1024, batch=1.
Дополнительный режим распределяет компоненты между 4070 Ti Super и 3080 Ti.
Веса и вычисления нейросетевых компонентов остаются на GPU, CPU-offload отключен.
Загрузка весов, токенизация, PNG и HTTP используют CPU/RAM.

## Подготовка

На хосте нужны существующие Docker с Compose (для dual override нужен Compose
2.24.4+), NVIDIA GPU runtime, Python 3 и `nvidia-smi`. Новые Python/Node-пакеты
на хост не устанавливаются. Все зависимости приложения находятся в образе.

Из корня проекта:

```bash
python3 prepare-sdxl.py
make sdxl-build
make sdxl-download
make sdxl-test
make sdxl
```

`prepare-sdxl.py` дописывает только отсутствующие SDXL-параметры в `.env`,
сохраняя текущие пароли и image digests. Он выбирает GPU по названию и сохраняет
UUID; уже заданные UUID не перезаписывает. При нескольких одинаковых картах
проверьте выбранные значения вручную. UID/GID должны иметь доступ к `outputs/sdxl`.
Для существующей установки не запускайте исходный `prepare.sh` повторно.

Образ закреплен на PyTorch 2.7.1 / CUDA 12.8 по digest, зависимости в
`sdxl/requirements.lock`. Базовый образ содержит Python 3.11. При обновлении
версий заново проверьте обе GPU и регенерируйте lock-файл в контейнере.
Штатный invisible watermark явно отключен (`add_watermarker=False`);
дополнительный пакет watermark не устанавливается.

Модель скачивается в `models/sdxl-base-1.0`, revision
`462165984030d82259a11f4367a4eed129e94a7b`. Загружаются только 19 необходимых
файлов FP16 pipeline и лицензия, без refiner и альтернативных checkpoint.
`manifest.json` создается после проверки набора файлов и вычисления SHA256.
Повторная загрузка использует кеш и проверяет файлы заново.
Локальные хеши не являются независимым подтверждением автора весов.

Runtime использует только локальные файлы, `HF_HUB_OFFLINE=1` и
`TRANSFORMERS_OFFLINE=1`. Веса подключены read-only и не встроены в образ.
При старте проверяются revision и размеры файлов; полная SHA256-проверка
выполняется загрузчиком, не на каждом рестарте.

## Запуск

UI: http://127.0.0.1:8082, OpenAPI: http://127.0.0.1:8082/docs.
Аутентификации нет; порт публикуется только на loopback, не выставляйте его
на внешние интерфейсы без отдельного контроля доступа.

```bash
make sdxl                 # одна карта
make sdxl-dual            # две карты, тот же сервис и порт
make logs-sdxl
curl --fail http://127.0.0.1:8082/health/ready
python3 smoke-test-sdxl.py
```

`make sdxl` и `make sdxl-dual` останавливают Qwen/Gemma перед запуском.
`make qwen` и `make gemma` останавливают SDXL. `make models-stop` останавливает
все модели. Веса, результаты и named volumes при этом сохраняются.
`.NOTPARALLEL` действует внутри одного make; не выполняйте независимые команды
переключения одновременно. Прямой `docker compose up` обходит переключение.
При запуске проверяйте свободную VRAM: другие приложения Docker/Windows могут
продолжать занимать GPU после остановки контейнеров моделей.

Переменная `COMPOSE` в Makefile остается переопределяемой, включая загрузку весов.
Пример: `make sdxl COMPOSE='docker --context default compose'`.

## API

```bash
curl --fail http://127.0.0.1:8082/api/generations \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"A glass pavilion beside a lake, morning light", "negative_prompt":"blur", "steps":30, "guidance_scale":5.0, "seed":42}'
```

Ответ 202 содержит UUID задания. Затем используйте:

| Метод | Путь | Результат |
|---|---|---|
| GET | `/api/generations` | История сохраненных заданий |
| GET | `/api/generations/{id}` | Статус, прогресс, параметры, метаданные |
| GET | `/api/generations/{id}/image` | Готовый PNG |
| DELETE | `/api/generations/{id}` | Отмена задания |
| GET | `/health/live` | HTTP-процесс отвечает |
| GET | `/health/ready` | Модель загружена и прогрета |
| GET | `/metrics` | Prometheus metrics |

Разрешены только 1024x1024 и одно изображение за запрос. Шаги 1–60,
guidance 1–15, seed 0–4294967295 или null для случайного значения.
Промпты ограничены 2000 символами на уровне API и длиной токенизаторов на
уровне задания. Слишком длинный промпт завершается явной ошибкой, без
незаметного усечения. Неизвестные поля отклоняются.

Один запрос исполняется, до четырех ожидают. Переполнение дает HTTP 429,
неготовность модели 503, некорректные параметры 422. Отмена активного задания
проверяется между шагами denoising; начавшийся VAE decode заканчивается перед
освобождением GPU. Следующее задание начинается только после завершения
предыдущего и необходимого восстановления pipeline.

PNG и JSON сохраняются в `outputs/sdxl`. По умолчанию хранятся до 100
завершенных заданий не старше 168 часов; очистка идет во время работы сервиса.
Промпты сохраняются в JSON результатов, но не включаются в метрики и обычные логи.
После рестарта незавершенные задания получают `interrupted`; готовые сохраняются.
В JSON также записаны revision, версии, seed, scheduler, размещение, время,
пиковая VRAM процесса и пиковая RAM процесса за его время жизни.

## Память и диагностика

`SDXL_GPU0` указывает UUID 4070 Ti Super, `SDXL_GPU1` UUID 3080 Ti.
Логические CUDA индексы внутри контейнера могут отличаться от индексов хоста;
проверяйте `pipeline.gpus` и `pipeline.placement` в readiness и JSON результата.
В single PyTorch видит одну GPU, в dual обе. Дополнительно к Docker reservation
задается `CUDA_VISIBLE_DEVICES`: в WSL ограничение устройств самим Docker
может не скрывать вторую карту от CUDA.

В dual используется `device_map="balanced"`, с бюджетами размещения весов
`SDXL_GPU0_BUDGET=11GiB` и `SDXL_GPU1_BUDGET=9GiB`. Это не жесткие лимиты пика
VRAM. Компоненты, оставшиеся на CPU/disk, делают pipeline неготовым.
28 GiB двух карт не являются единым непрерывным пулом памяти.

VAE tiling включен по умолчанию с плиткой 512 пикселей: штатный порог SDXL
1024 не разделяет изображения нашего размера. Tiling может немного менять
изображение на границах перекрывающихся плиток. Первый прогон без ограничения
аллокатора исчерпал свободную VRAM.
Аллокатор PyTorch ограничен свободной памятью при старте минус
`SDXL_VRAM_RESERVE_GIB` (по умолчанию 1.5 GiB). Это оставляет резерв под драйвер
и другие приложения; их рост после запуска требует отдельного контроля.

При OOM сервис не переходит на CPU и не уменьшает запрошенный размер.
Проверяет восстановление с прогревом; если оно не удалось, readiness становится
503 и процесс корректно завершается. Docker перезапускает сервис по политике
`unless-stopped`; при повторении ошибки остановите сервис и устраните причину.
Сначала освободите GPU от других приложений, проверьте `SDXL_VAE_TILING=1`
и пересоздайте сервис через make либо сравните с dual-режимом.
VAE при необходимости использует FP32 на GPU для стабильного decode.

Проверяйте `nvidia-smi` и в Windows Shared GPU memory: CUDA-размещение само
по себе не доказывает отсутствие вытеснения драйвером в RAM.
Измеренное `process_peak_rss_bytes` включает холодную загрузку, это не текущая RAM.

## Проверки и мониторинг

```bash
make sdxl-test
python3 smoke-test-sdxl.py --count 10
python3 smoke-test-sdxl.py --count 10 --duration 1800
```

Отчеты сохраняются в `outputs/sdxl/benchmarks`. Smoke-тест декодирует PNG и
проверяет размер и разброс пикселей; качество нужно оценивать визуально.
Сравнивайте одинаковые шаги/размеры для single и dual; межкарточный обмен
может замедлить генерацию. Seed не обещает побитового совпадения между режимами.

Grafana: http://127.0.0.1:3055/d/local-sdxl. Dashboard показывает готовность,
очередь, длительность, ошибки/OOM и GPU. Логи SDXL доступны в общем dashboard
моделей. Метрики GPU относятся ко всей машине. Остановленный профиль SDXL
не вызывает ScrapeTargetDown; работающий, но долго неготовый сервис вызывает
SdxlNotReady. Для подхвата изменений конфигурации уже запущенного стека:

```bash
docker compose up -d alloy
docker compose restart prometheus alloy
```
