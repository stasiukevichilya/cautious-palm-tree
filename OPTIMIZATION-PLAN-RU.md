## 1. Найденные слабые места

### 1.1. Scraper

| # | Приоритет | Проблема | Где |
|---|-----------|----------|-----|
| S1 | P0, баг | **Суте́чный отчёт включает давно удалённые объявления.** `report()` берёт все записи `listings` по watch без фильтра «живости»: таблица только пополняется, `last_seen_at` при обновлении, но мёртвые объявления никто не убирает. Через несколько недель отчёт «актуальные цены» будет показывать мёртвые лоты. | `scraper/service.py: report()`, `scraper/store.py: listings()` |
| S2 | P0, баг | **Один плохой получатель блокирует доставку всем последующим.** В `_deliver_alerts` `try` оборачивает весь цикл по пользователям: если `notify_user` для первого пользователя упал (409 — пользователь заблокирован, сбой сети), остальные пользователи в этом раунде не получают свои алерты вообще. Заблокированный пользователь дополнительно держит алерт pending и заставляет повторять попытку каждый скрейп в течение 7 дней. | `scraper/service.py: _deliver_alerts()`, `scraper/tgbot.py: notify_user()` |
| S3 | P0, perf | **Commit (и fsync) на каждую строку.** `upsert_listing`, `add_price_point`, `add_alert`, `record_scrape` делают `COMMIT` каждая. При 50–200 объявлениях на watch это сотни fsync за один скрейп (WAL + `synchronous=NORMAL`). | `scraper/store.py` (все методы), `scraper/service.py: scrape_watch()` |
| S4 | P1 | **Неограниченный рост `price_history`.** Точка цены пишется для каждого увиденного объявления на каждом скрейпе. Без очистки таблица растёт ~500–1000 строк/день. `alerts` (доставленные) тоже не чистятся. | `scraper/store.py`, `scraper/service.py: scrape()` |
| S5 | P2 | `POST /api/scrape` принимает `body: dict | None` без валидации (любой JSON проходит в `watch_ids`). | `scraper/app.py: scrape_now()` |

## 2. План работ

### Фаза 1 — баги (делать сейчас)
1. **S2**: доставка алертов по пользователям независимо друг от друга; 409 от tgbot —
   отдельное исключение `Refused`, такие алерты помечаются доставленными (повтор бесполезен),
   остальные пользователи получают свои алерты в этом же раунде. Тест: два получателя,
   один отказан — второй получил.
2. **S1**: `store.listings(since=...)`; отчёт использует только «живые» объявления
   (`last_seen_at >= now - SCRAPER_ALIVE_WINDOW`, по умолчанию 2 ч — с запасом на
   несколько проваленных скрейпов при интервале 15 мин). Тест: старое объявление
   в отчёт не попадает.
3. **T2**: в движке у каждого metadata-only торрента время создания; `tick()` удаляет
   записи старше `metadata_ttl` (по умолчанию 1800 c — больше TTL кнопки бота),
   метрика `metadata_fetches{result="expired"}`. Тест: старая запись удаляется тиком.
4. **T1**: у клиента бота отдельный таймаут для `metadata()` —
   `TGBOT_TORRENT_METADATA_TIMEOUT` (по умолчанию 240 c = таймаут движка + запас).
5. **B1**: текст `/sessions` режется в 20 строк + «… ещё N».

### Фаза 2 — производительность и порядок
6. **S3**: в `store` — явные транзакции (`isolation_level=None`, контекст
   `transaction()`), `scrape_watch` собирает страницу в fetch (вне транзакции),
   а запись upsert/price-точек/алертов делает одной транзакцией на watch.
7. **S4**: `store.prune()` в начале полного скрейпа: `price_history` старше 30 дней
   и доставленные алерты старше 30 дней.
8. **S5**: `ScrapeIn` pydantic-модель для `POST /api/scrape`.
9. **T4**: при удалении торрента убирать gauge-серии (если версия prometheus_client
   поддерживает `.remove`), иначе оставить обнуление.

### Фаза 3 — персистентность и порядок (завершён 01.10.2026)
10. **T3**: персистентность очереди торрентов (JSON на volume + re-add при старте).
    Реализовано: реестр зеркалируется в `queue.json` рядом с каталогом загрузок
    (`/data/queue.json`, тот же volume), записывается атомарно (tmp + `os.replace`)
    при каждом изменении состояния; при старте `Engine.start()` перечитывает файл и
    re-add'ит торренты (magnet хранится в записи; data с диска подхватывается по hash).
    `metadata`-записи восстанавливаются как metadata-only (TTL продолжает течь с
    сохранённого `created`), `failed` — намеренно не восстанавливаются.
11. **B2**: серверный эндпоинт поиска watch по (source, ref) вместо полного списка.
    Реализовано: `GET /api/watches/find?source=&ref=` (404 — нет такого watch),
    `Market.find_watch` в боте ходит точечным запросом; 404 → `None`, остальные
    ошибки — как раньше.
12. **B3**: отдельные ключи на сервис — не делать, пока стек на loopback.

### Что изменилось в коде (фаза 3)
- `torrent/engine.py`: реестр зеркалируется в `queue.json` (том же volume, что и
  загрузки): `_save_queue()` (атомарно, best-effort) вызывается при создании записи,
  смене состояния, удалении и TTL-drop; `load_queue()` в `start()` re-add'ит
  `metadata`/`downloading`/`seeding`-записи (magnet и peer-хинт хранятся в записи,
  `connect_peer` сразу после `add_torrent` — отложенный connect молча сбрасывается);
  повреждённый/старый формат файла не роняет старт (`.get` на полях, skip с лог-строкой).
- `torrent/tests/test_engine.py`: +5 (восстановление загрузки до конца после «смерти
  процесса», восстановление pending-metadata, битый файл, старый формат без `peer`,
  удаление из файла). Примечание: в тестах «рестарт» — полное разрушение старой
  libtorrent-сессии; простой `pause()` оставляет живые сокетy старой сессии, и те

  процесс умирает и ядро закрывает сокеты).
